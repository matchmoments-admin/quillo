## 1. The diagnosis

Quillo never assigned an owner to each of the four questions a tax-prep app must answer — *where do I stand*, *what's left*, *where do I enter this fact*, and *where do I decide deductibility* — so every slice answered whichever question was in front of it and, because the working agreement requires additive + flag-gated change, left the previous answer standing beside it. The measurable result is eight independent implementations of "what's left before I can file" (progress.ts, queries.dashboard, generateChecklist, SetupChecklist, claim_suggestions, accountantSuggestions, scan.ts, assessReadiness) and two-to-three editors for single facts like WFH hours, car km and loan interest — while the one rigorous model, the pure, LLM-free, denylist-tested `assessReadiness`, is rendered by exactly one component in the whole SPA (Filing.tsx:84), the last page a user reaches. The Dashboard is the page with no question of its own: its subtitle names a data shape ("What you've tracked") rather than a user need, so it became the default landing spot for every answer that had nowhere else to live — a status board, a to-do list and two multi-field tax calculators on one scroll. The 85-of-87 permanently-on flags are not the disease; they are the mechanism by which each superseded answer was permitted to stay, which is why the file *reads* even heavier than it renders. Fix the ownership — one engine owns readiness, one page owns each fact — and the component count collapses without removing a single capability.

### F1. Stop hiding the Assets nav item under payg_express — the eligibility test never looks at depreciating assets

`blocker` · `CONFIRMED` · effort S · surface: journey-chrome

**Files** — `web/src/App.tsx:41`, `web/src/App.tsx:262-271`, `src/lib/db.ts:114-127`, `src/lib/db.ts:160-181`

**What the user experiences.** A single-PAYG taxpayer (one `self` person, only `individual`/`employment` entities, no properties, no business/rental activity, no CGT assets) loses the "Assets" entry from the sidebar AND from the mobile "More" drawer, because both render from the same filtered GROUPS. There is no other navigable entry point: grep shows only App.tsx:41 and two conditional links inside Filing.tsx:28 / Filing.tsx:364, and the Filing "Add an asset" link only appears once a div40 claim already exists — which requires an asset. The user must type /assets manually.

**Why it's a problem.** `paygExpressEligible` (src/lib/db.ts:114-127) tests persons, entity kinds, `properties`, `income_activities` and `cgt_assets`. It does NOT count rows in the `assets` table (schema.sql:692), the depreciating-asset table that drives decline-in-value. So a PAYG-only nurse or renter who bought a $2,000 laptop is "express eligible" and has the only UI entry point to that deduction removed — and worse, a tenant who ALREADY has assets rows keeps them hidden, so an existing depreciation schedule silently becomes unreachable. This violates the CLAUDE.md "engine ✓ + UI ✓ + display ✓" contract: the Div 40 engine is live, the UI is now unreachable for the personas most likely to need the simple case.

**Proposed change.** Two changes. (a) Add `assetN` to `paygExpressEligible`'s input and require it to be 0 — same `try/catch` shape as the existing counts in src/lib/db.ts:167-176, plus a golden in scripts/check-units.ts:684 for "PAYG with one depreciating asset ⇒ NOT express". (b) Better still, stop hiding the item at all: hiding exactly 1 of ~18 destinations buys almost no simplicity while carrying real completeness risk. Repurpose payg_express to demote Assets into the "More" disclosure (SECONDARY_GROUPS, App.tsx:255) rather than removing it, so the surface is quieter but never unreachable.

**Persona risk.** Personas 1 (Maya, PAYG renter — small work deductions), 7 (Nadia, nurse — self-education equipment) and 3 (Lukas, tradesperson — tools/PPE, if his cash side job is not recorded as a business activity) all satisfy the current eligibility predicate and all can legitimately hold depreciating assets. They currently cannot get tax-ready with decline-in-value. Fix (a) is the minimum; fix (b) makes the class of bug impossible.

**Verifier evidence.** src/lib/db.ts:114-129 `paygExpressEligible` tests only persons/entities/properties/businessOrRentalActivityN/cgtAssetN — the `assets` table is never counted; src/lib/db.ts:167-170 confirms the two live COUNTs are over `income_activities` and `cgt_assets` only. web/src/App.tsx:41 marks `{ to: "/assets", … expressHidden: true }` and App.tsx:271 filters it out when `paygExpress`; the mobile "More" drawer renders the same Sidebar (App.tsx:180 → setDrawer, App.tsx:266 comment), so both navs lose it. `payg_express` IS in wrangler.toml:80 FEATURES, so this is live. Exhaustive grep for `/assets` in web/src returns only App.tsx:41, JourneySpine.tsx:22 (a `match` entry — the Bring-in pill's href is /accounts, not /assets), Filing.tsx:28 and Filing.tsx:364. Assets.tsx:130 `api.addAsset` is the ONLY asset-creation UI in the SPA. The smoking gun: scripts/check-personas.ts:63-71 seeds persona 1 (Maya) with exactly one `self` person, zero entities, zero properties, zero cgt_assets — i.e. `paygExpressEligible` returns true — AND two `assets` rows ('p1aMon' monitor, 'p1aLap' laptop) with a depreciation_schedule. The repo's own #1 persona is a tenant whose live Div 40 schedule has no navigable UI.

**Verifier correction _(authoritative)_.** Two of the finding's supporting details are slightly off but do not change the verdict. (a) Filing.tsx:364's "Add an asset" link fires on a `div40` CLAIM, not on an existing asset row — but grep of src/rulepacks/au-v1.json shows the only `"claim_type": "div40"` rule is `au-rental-decline`, scoped to `bucket=property_rented`, which a payg-express tenant (properties.length===0) can never hit. Filing.tsx:28's "Review assets" link needs a readiness finding with `evidence_refs[0].kind === "asset"`, which src/lib/readiness.ts:448/535 only emit for needs-review or disposed assets that already exist. So the finding's conclusion — no practical entry point — holds. (b) Proposal (b) as written isn't directly implementable: SECONDARY_GROUPS (App.tsx:255) is keyed by GROUP LABEL, and Assets is an ITEM inside "1 · Bring in"; demoting a single item needs a new per-item `secondary` flag, not a SECONDARY_GROUPS entry. Fix (a) — add `assetN` to the predicate and a check-units golden alongside scripts/check-units.ts:685-699 — is the minimum and is correct as specified.
